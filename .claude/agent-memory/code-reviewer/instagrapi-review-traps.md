Real instagrapi behaviour to check any fake Client against (verified 2026-09-19, instagrapi 2.2.1, #133 review):
- `private_request` with `handle_exception=None` routes ChallengeRequired into `challenge_resolve`, which can call `manual_input_code` -> `input()` (hang in TTY / EOFError on dyno) or raise ChallengeError subclasses (ChallengeUnknownStep, ChallengeRedirection, ChallengeSelfieCaptcha). A raw `ChallengeRequired` rarely escapes `login()`, so `except ChallengeRequired` backoff is mostly unreachable in prod.
- `photo_upload` first calls `photo_rupload` via `self.private.post` (not private_request): non-200 -> `PhotoNotUpload`, never LoginRequired. LoginRequired only comes from `photo_configure`/`expose`.
- `login()` returns early when `user_id` set and not relogin (auth.py ~421); relogin=True clears cookies/auth; ReloginAttemptExceeded after 2.

**Why:** fakes that raise ChallengeRequired/LoginRequired directly let tests pass while prod takes the generic-Exception branch (no 24h block -> password-login loop).
**How to apply:** for any Instagram publisher change, ask whether handle_exception/challenge_code_handler is set and whether generic failures after clearing the session back off. Related: [[storage-protocol-review-traps]]

Accepted fix pattern (#133 round 2): `client.handle_exception = _reraise` (verified: private_request then never calls challenge_resolve) + session check via `get_timeline_feed()` after restoring settings. Watch for over-broad "relogin_started" flags that back off 24h on unrelated upload errors after a *successful* relogin.
- Fingerprint carry-over trap: `set_device()` does NOT recompute `user_agent` (auth.py ~641-672); also call `set_user_agent(stale["user_agent"])`. `Client()` uses a shared mutable default `settings={}` across instances, so ad-hoc experiments with two default Clients leak state — use `Client(settings={})` when verifying.
- Device context beyond uuids/device_settings/user_agent (verified empirically 2026-09-20): a real `get_settings()` dump also holds `country`, `country_code`, `locale`, `timezone_offset`, `mid`, `ig_u_rur`, `ig_www_claim`. `set_settings()` -> `init()` restores all of them; a hand-rolled `_carry_device` that only calls `set_uuids`/`set_device`/`set_user_agent` silently resets country/locale/timezone_offset to instagrapi defaults (US/en_US/-14400) and drops `mid`. `base_headers` sends them as `X-IG-App-Locale`, `X-IG-App-Startup-Country`, `X-IG-Timezone-Offset`, `X-MID` — so a "fingerprint-preserving" relogin can still arrive with a changed device context. A verbatim stored `user_agent` survives, which is why a UA-only assertion passes.
- `set_settings()` on a partial dict (only uuids/device_settings/user_agent) does NOT raise: `init()` uses `.get()` throughout. Storing a fingerprint-only session as a crash-safe placeholder is safe against the real Client.
- Classifying a failed `login()` (verified 2026-09-20, #133/PR #154): use an allow-list of *transient* errors and treat everything else as a verdict. A verdict tuple cannot be made safe — `ClientThrottledError` (HTTP 429, `private.py` status branch) is a **direct `ClientError`**, not a `PrivateError`/`RateLimitError`, so no tuple of throttling types catches the likeliest throttling signal. Also outside the obvious families: `FeedbackRequired`, `SentryBlock`, `ProxyAddressIsBlocked` (all `PrivateError`), `CaptchaChallengeRequired` (direct `ClientError`, *not* a `ChallengeError`), `BadCredentials` (*not* a `BadPassword`). The `*Form` challenge classes (Recaptcha/SubmitPhoneNumber/SelectContactPoint/LegacyForceSetNewPassword) ARE `ChallengeError` subclasses. `ClientJSONDecodeError` is not transient: `raise_for_status()` runs before `.json()`, so it only fires on a 200 with a non-JSON body — during login that is an HTML checkpoint page. `private_request` wraps only `requests.HTTPError` and `requests.ConnectionError`; instagrapi passes no `timeout=`, so `ReadTimeout` never fires.
- `set_user_agent("")` renders `config.USER_AGENT_BASE.format(**device_settings)` and raises **KeyError** on a partial `device_settings` dict. Any code that derives a UA from carried device settings must tolerate that (or validate the dict) — a real `get_settings()` dump is complete, a hand-edited or truncated stored fingerprint is not.
