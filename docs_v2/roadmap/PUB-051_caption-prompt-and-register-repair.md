## User Story

As a publisher operator curating content, I want the caption prompt to vary what it asks for, stop re-inviting the shapes it was meant to remove, and give each platform a stance rather than a list of adjectives, so that captions differ from one another in the ways a reader notices.

## Problem

All verified by running the real prompt builder with a fake client (review [#177](https://github.com/dhirmadi/SocialMediaPythonPublisher/issues/177), captions H2, M1, M2, M3):

1. **The structure-directive rotation has one state.** `utils/captions.py:329-348` `classify_caption_structure` maps any two-sentence caption without `?` to `observation` and can only return `declarative` for a single sentence of eight or more words, so `pick_structure_directive` (`:351-369`) returns "Open with a plain declarative statement." on every run, for every platform, including the regeneration retry.
2. **The closing-avoid line is counterproductive.** `caption_closing_pattern` (`:377-384`) classifies a plain sentence as `statement`; the rendered constraint then says "avoid: statement", and the natural alternative for a 30-word email subject is the question #138 removed. With `closing: any` the line is always emitted.
3. **The prompt is 8:1 instruction to output.** With history and a profile the user message is about 1,180 tokens: 24 quoted "openings to avoid" in the house register, "Use DIFFERENT openings" three times while every platform gets the same directive, and about 460 tokens of analysis rendered as Python repr with hex colours and 15 to 25 snake_case tags (`build_analysis_context`, `services/ai.py:606-666`) against about 40 tokens of persona.
4. **The SD prompt shares the completion.** `generate_multi_with_sd` (`ai.py:1354-1405`) produces every caption and `sd_caption` in one JSON object; the prompt-engineer brief pulls diction toward its nouns.
5. **Sampling.** Temperature 0.7, presence 0.6, no frequency penalty (`ai.py:101-104`). Presence acts within a completion, not across runs.
6. **The vision register pins the vocabulary.** `ai_prompts.yaml:1-5` makes the vision model a "neutral analyst"; `:33-35` briefs the caption-facing `sensory_detail` with five fixed nouns (texture, tension, temperature, gaze, breath) at temperature 0.4. The in-code default that tried to state both registers (`ai.py:191-233`) is dead because the YAML wins (`:448`).
7. **Email has no register after #138**, and telegram's "conversational, emoji-friendly, artistic commentary" is the register of the tells. `caption_history` records rows for platforms that failed (`core/workflow.py:772-783`), and a partial retry re-pays vision and caption instead of reading the sidecar it wrote.

## Desired Outcome

Exactly one content angle per platform per call, rotating across runs from an explicit stored column. No closing-pattern constraint. A caption user message under 500 tokens with history and a six-example profile, with the analysis as a short prose paragraph after the brief. Captions and the SD prompt in separate completions. Caption-facing vision fields produced under the owner persona with a rotating senses pool. Each platform brief names who is speaking to whom. History records only published captions; a partial retry costs zero OpenAI calls when the sidecar holds the captions.

## Scope

**In scope:**
- Replace `STRUCTURE_DIRECTIVES` with a content-angle pool (see AC1 for the pool itself) rotated by an `angle` column stored with each caption (additive migration); delete `classify_caption_structure`. Concretely: a new nullable `angle` column on `CaptionHistory` (`db/models.py`) plus a new Alembic migration (`004_*.py`, following the `001_create_caption_history.py` pattern — BigInteger PK for Postgres, Integer for SQLite tests); `CaptionStore.save_captions_batch` gains an `angles_by_platform: dict[str, str] | None` parameter; `CaptionStore.fetch_recent_by_platform` (or its equivalent) returns each row's `angle` so rotation reads the stored value directly instead of reverse-classifying caption text; `AIService.create_multi_caption_pair_from_analysis` must return the chosen angle per platform alongside captions/`sd_caption` so `WorkflowOrchestrator`'s existing `caption_history_saved` call site (`core/workflow.py`, `_caption_store.save_captions_batch(...)`) can thread it through. `excluded_directives` (`services/ai.py:676-683`) carries the same per-platform exclusion contract forward against the new angle-pool keys.
- Delete the closing-pattern constraint; openings-to-avoid cut to the last two (cap the rendered list itself in `build_platform_block`/`build_history_block`, independent of how much history the caller fetched); emoji and hashtags stripped from history before deriving constraints
- Analysis rendered as prose after the brief, capped at about 120 tokens; `color_palette`, `tags`, `aesthetic_terms` dropped from the caption prompt
- `sd_caption` moved from the caption-stage completion (`generate_multi_with_sd`) into the vision stage; caption completion keys are platforms only (no `sd_caption` key requested there anymore)
- Caption call `temperature=0.9`, `frequency_penalty=0.3`, `presence_penalty=0.6`
- `caption.rules` extended to ban every pattern in `utils/caption_metrics.DEFAULT_TELLS_LEXICON` (PUB-049's measured tells), rendered as positive replacements, not just an extended "never use" list; default persona rewritten as a person; rope-specific persona moved to the tenant `system_prompt` example in docs
- Vision: second small call for `sensory_detail` and `mood_note` under the owner persona at temperature 0.9 with a rotating senses pool (or a two-register system prompt; the PR states the choice and cost — either is acceptable, see AC5); dead `_DEFAULT_VISION_*` constants removed (preferred — nothing else needs them once the YAML always wins per Problem #6); `sd_caption` stays on whichever vision-stage call carries the neutral/analyst system prompt (the existing metadata register), never the new warm owner-persona call, since its PG-13 fine-art brief matches the neutral register
- **Sequencing constraint (real regression risk, not optional):** AC4 (caption completion stops requesting `sd_caption`) and AC5 (vision starts producing it) must land in the same deploy even though they are separate PRs (#191, #192) for review purposes — between the two, `core/workflow.py`'s `if sd_caption and not debug and not dry_publish and not preview_mode:` sidecar-write guard (`:642`) would be false for every image, silently disabling the sidecar's `sd_caption` write. Either merge #191 and #192 together, or reorder so #192 (vision produces `sd_caption`) merges first.
- `CaptionGeneratorOpenAI`'s SD-prompt tenant-override resolution (`services/ai.py:895-964`: `sd_caption_system_prompt`/`sd_caption_role_prompt`/`sd_caption_brief`/`sd_caption_model`) and the `sd_caption:` block in `ai_prompts.yaml` lose their only caller in the multi-platform path once AC4/AC5 land. State explicitly in the #192 PR body whether this is removed as dead code, or kept because the single-platform fallback (`generate_with_sd`/`create_caption_pair_from_analysis`) still uses it — do not leave it in place unaddressed.
- `AIService.create_multi_caption_pair_from_analysis`'s return arity changes to also carry the chosen angle per platform. Both existing call sites — `core/workflow.py:604` and `web/service.py:909` — must be updated in the same change; this is an internal service contract, not a public CLI/web API, so changing its arity is acceptable, but only if both callers move together. `CaptionStore.fetch_recent_by_platform` keeps its existing `dict[str, list[str]]` return shape and its ~8 existing tests in `test_caption_history_db.py` untouched (it has two callers — `core/workflow.py:564` and `web/service.py:899` — beyond just the rotation path); add a new sibling method (e.g. `fetch_recent_with_angles_by_platform`) for the angle-aware read the rotation needs, rather than breaking the existing one's contract.
- The similarity-gate regeneration path (`_apply_similarity_gate`/`_generate_once`, `services/ai.py:1565-1622`) must track which angle was just chosen per platform on the rejected attempt, so the next pick (AC1's third test) can exclude it — today that function only tracks `directives` keyed by `excluded_directives`, not "what was just picked this attempt."
- Platform stances in the YAML `style`; history saved only for published platforms (fix: the `core/workflow.py` `caption_history_saved` call currently iterates `enabled_publishers` unconditionally — it must filter to platforms with a successful `publish_results` entry, per Problem #7); retry reuses `caption_generated` from the sidecar; a non-JSON vision reply retried once before the expensive fallback

**Out of scope:**
- Candidate generation and selection (PUB-052)
- Voice corpus plumbing (PUB-050)
- Any platform limit change
- Adding a tokenizer dependency (e.g. `tiktoken`) for AC3's token count — see AC3

## Acceptance Criteria

- AC1: Given a fixed content-angle pool of at least five entries (e.g. `sensation`, `moment`, `craft`, `atmosphere`, `direct_address` — analogous in shape to today's `STRUCTURE_DIRECTIVES`, but naming *what the caption dwells on*, not *how it opens*), a stored `angle` per history row (read directly, not reverse-classified from caption text), and realistic history, when the prompt is rendered three times, then each platform receives exactly one angle per call and the angle differs across the three runs (least-recently-used over the stored column, ties broken by pool order, mirroring today's `pick_structure_directive` contract); the regeneration path picks a different angle from the rejected draft's angle
- AC2: Given any history, when the prompt is rendered, then no "closing pattern" line is present anywhere (not just when a closing is mandated) and at most two openings-to-avoid appear per platform, regardless of how many history items were fetched
- AC3: Given history and a six-example profile, when the prompt is rendered, then the user message is under 500 tokens, measured as `len(prompt) / 4` (the standard ~4-chars-per-token approximation; no `tiktoken` or other new dependency — pin this exact formula so the test is deterministic), and contains no hex colour or snake_case tag. *Clarified 2026-09-26 (implementation):* the bound applies to the test fixture (three platforms, eight-deep history, six ~60-character voice examples); it cannot hold for every tenant, because `DEFAULT_VOICE_PROFILE_TOKEN_BUDGET` (PUB-029, 500 tokens) lets the examples alone exceed it. Heavier profiles are guarded against growth by `test_heavy_tenant_user_message_stays_under_600_tokens` (measured ~570 with 120-character examples and seed hashtags).
- AC4: Given the caption call, when the fake client records the request, then the JSON keys the model is asked to return (the prompt's key list and the parsed response dict) are the enabled platforms only — no `sd_caption` key — and `temperature`, `frequency_penalty` and `presence_penalty` on the actual `chat.completions.create(...)` call equal the configured values (`response_format` itself stays `{"type": "json_object"}` as today; this AC is about the requested/parsed platform keys, not that parameter)
- AC5: Given the vision stage, when the fake client records the requests, then `sd_caption` comes from whichever vision-stage call carries the unchanged neutral/analyst system prompt and is written to the sidecar unchanged; and the caption-facing fields (`sensory_detail`, `mood_note`) are produced under an owner-persona framing, asserted via a fixed, implementation-independent marker string (e.g. `OWNER-VOICE SECTION:`) that must appear in whichever system message governs those two fields — a second call's entire system message (two-call design) or a clearly delimited section within the one combined system message (single-call two-register design). This lets the test-engineer write the test before a developer picks which of the two designs to build, per the scope's explicit either/or.
- AC6: Given two images, when the senses pool is rendered, then the *constructed prompt text* (the pool subset/order offered to the model, seeded from the image content hash — not the model's actual output, which cannot be asserted deterministically) differs by seed (`test_senses_pool_prompt_text_differs_by_image_seed`); separately, given the sidecar's phase-2 metadata after a run through the two-call (or two-register) vision stage, then the caption-facing fields (`sensory_detail`, `mood_note`) are absent from it (`test_caption_facing_fields_stay_out_of_sidecar_after_vision_restructure` — a regression guard on the existing `core/models.py` invariant, now worth re-testing because the vision stage gained a second call/register)
- AC7: Given a partial publish followed by a retry through the real orchestrator with fake publishers, when both runs complete, then vision and caption fakes were called once in total (the retry makes zero AI calls, reading `caption_generated` from the sidecar) and `caption_history` holds exactly one row per platform whose `publish_results` entry succeeded — not one row per configured/enabled publisher, which is today's bug (Problem #7)
- AC8: Given a vision reply that fails JSON parsing specifically (not a network/transient error, which the existing `@_ai_retry` decorator already covers), when the analyzer runs, then it is retried exactly once at the same resolution and detail before falling through to the (different-resolution) fallback path
- AC9 (verification, not a `pytest` AC — see Implementation Notes): Given the PUB-049 harness's `--nightly` mode run on this item's branch, when its score table is compared to the PUB-049 baseline snapshot, then opener share and tells rate improve and TF-IDF cosine to history does not rise; the table is pasted into the PR body per each of the three sub-PRs (#191, #192, #194), not asserted by an automated CI gate

## Implementation Notes

- Three sub-issues, three PRs, and this spec's ACs map onto them as follows — AC1, AC2, AC3, AC4 → #191 (prompt and sampling); AC5, AC6, AC8 → #192 (vision register); AC7 → #194 (stances, history, retries); AC9 (the harness table) is produced and pasted into all three PR bodies, since each is a real behavior change the harness can see. **#191 and #192 must merge together or with #192 first — see the sd_caption sequencing constraint in Scope; do not ship #191 alone.**
- Tests assert structure (angle count, line absence, token bound, JSON keys, call sequence), not wording; this starts the PUB-060 rewrite of the 59 substring tests.
- The `angle` column is an additive migration (new nullable `CaptionHistory.angle`, new Alembic version file, `CaptionStore` read/write surface extended — see Scope for the exact touch points); list it in the PR body. Existing rows with `angle IS NULL` must be treated as "never used" by the rotation (same bucket the old `pick_structure_directive` used for unclassified history), not as an error.
- AC9's token/harness verification is explicitly **not** given a `pytest` function name — it is a human-run step (like the old PUB-049 "close #146/#138" note), because it requires a live OpenAI key and a nightly-mode run, which is outside what CI's offline gate can do. Do not invent a fake test name for it in the handoff table.
- `caption.rules`' "measured tells" are `utils.caption_metrics.DEFAULT_TELLS_LEXICON` — import or otherwise keep this list as the single source of what counts as an AI tell; do not hand-maintain a second, divergent list in the YAML copy. The YAML text is prose guidance for the model, not the regex list itself, but every pattern in the lexicon should have a corresponding "write X instead of Y" line.
- The senses-pool seed (AC6) uses the same formula PUB-050 uses for voice-example sampling (`int.from_bytes(sha256(content)[:8], "big")`) — both items are meant to be independently developable (neither declares the other as a dependency), so implement this one-line formula directly in this item's own code rather than importing a helper from PUB-050's branch/PR. The trivial duplication is cheaper and safer than a cross-item coordination dependency.
- AC3's `len(prompt) / 4` is a deliberate proxy for OpenAI's actual tokenizer (reusing the convention already established by `truncate_history_to_budget`/`truncate_voice_profile_to_budget`, `services/ai.py:786-793`), not a live tokenizer call — the "under 500 tokens" claim in Desired Outcome is relative to this formula, not a literal guarantee against punctuation/JSON-heavy text under OpenAI's real tokenizer. State this once in the #191 PR body so it isn't later mistaken for an exact count.

## Risks

- Temperature 0.9 raises overshoot on the 240-character email subject; the condense pass guards length, and AC9 catches a tells regression.
- Moving `sd_caption` to the vision call changes which model writes it (gpt-4o instead of gpt-4o-mini); slightly higher cost, better SD prompts. State it in the PR.
- The vision stage gaining a second call (if that implementation is chosen over the two-register single call) roughly doubles vision cost per image; state the choice and the measured cost delta in the #192 PR body, per Scope.
- The `angle` migration is additive and backward-compatible, but until it is deployed and has accumulated some history, the first few runs on a tenant will have entirely `NULL`-angle history and the rotation degrades gracefully to "everything looks never-used" — equivalent to today's cold-start behavior, not a regression.
- **Pre-existing, out-of-scope risk worth flagging, not fixing here:** `VisionAnalyzerOpenAI` has no `_rate_limiter` at all today — `AIService.__init__` (`services/ai.py:1436-1439`) wires the shared rate limiter into `self.generator` only, and `core/workflow.py:486` calls `self.ai_service.analyzer.analyze(...)` completely unwrapped. This item adds a second vision-stage call (AC5/AC6 two-call design), which doubles an already-unbounded vision-call surface. Wiring the rate limiter into the analyzer is a small, well-understood fix (mirroring the one-line `self.generator._rate_limiter = self._rate_limiter` assignment) but is a scope decision, not something to add silently here — flag it to the user as a candidate follow-up item rather than folding it into this PR unannounced.
