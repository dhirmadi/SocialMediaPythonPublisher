## User Story

As an admin, I want every mutating route to enforce the same authentication and CSRF rules and every library operation to refuse a request that would destroy data, so that a stolen cookie or a stray API call cannot do what the UI would never do.

## Problem

The #75 and #128 hardening rounds landed the right checks but not uniformly (review [#177](https://github.com/dhirmadi/SocialMediaPythonPublisher/issues/177), security M1, M4, L1, L2, L3; all probed against the real app):

1. `POST` and `GET /api/config/voice-profile` (`web/app.py:853-878`) call `require_admin` only; every other mutating route calls `require_auth` first, and the `WEB_REQUIRE_HEADER_AUTH_WITH_COOKIE` check lives only in `require_auth` (`web/auth.py:89-94`). With strict mode on, a cookie alone gets 401 on analyze and 200 on voice-profile, and the profile feeds the caption prompt.
2. `web/middleware_csrf.py:84` skips CSRF whenever an `Authorization` header is present, verified or not; `api_auth_logout` (`web/app.py:410`) has no auth dependency. A bogus Bearer plus a cookie logs the session out without `X-Requested-With`.
3. `web/app.py:193` keeps FastAPI's default `/docs`, `/redoc`, `/openapi.json`, exposing every route and the upload contract anonymously on every tenant host.
4. `web/routers/library.py:64` allows `target_folder="root"`, and `:490-505` always takes the source as `image_folder`, so `src_key == dst_key`; `ManagedStorage.move_object` (`managed_storage.py:697-710`) copies then deletes unconditionally. R2 and MinIO accept a same-key copy, so the object and its sidecar are deleted.
5. `_sanitize_filename("foo.txt")` passes (`library.py:208-230`); upload writes JPEG bytes under a sidecar name; delete has no listing check; upload silently overwrites an existing image.

## Desired Outcome

`require_admin` enforces strict mode itself, so no route can forget it. CSRF is bypassed only by a header that verifies. OpenAPI is not served anonymously. A move can never produce a same-key copy-then-delete. Upload and delete operate only on image keys the listing knows, and overwrite is explicit.

## Scope

**In scope:**
- Strict-mode check moved into `require_admin`
- CSRF bypass conditional on `_verify_bearer` or `_verify_basic` succeeding
- `docs_url=None, redoc_url=None, openapi_url=None`; optional admin-gated alternative
- Move: reject `src_key == dst_key` with 400; derive the source prefix from the object's actual folder
- Upload: allowed image suffix only (415 otherwise); 409 on an existing name unless `overwrite=true`
- Delete: image suffix required and `ensure_known_image` reused
- `.claude/rules/web-security.md` and the endpoint contract in `ARCHITECTURE.md` updated

**Out of scope:**
- Rate-limit keys (PUB-053)
- Key derivation (PUB-053)
- Any CSP change

## Acceptance Criteria

- AC1: Given `WEB_AUTH_TOKEN` is set and `WEB_REQUIRE_HEADER_AUTH_WITH_COOKIE=1`, when a request with a valid admin cookie and no header hits `POST` or `GET /api/config/voice-profile`, then the response is 401 with the existing strict-mode message. Mechanism: move the strict-mode check (currently only inside `require_auth`, `web/auth.py:89-94`) into `require_admin` itself, run after its existing `is_admin_request` check succeeds — `require_admin` becomes self-sufficient for strict mode regardless of whether `require_auth` ran first, which is what makes AC2 provable without a per-route audit. **The new check must itself re-verify the header, not merely check that strict mode is configured**: `require_auth`'s existing check is implicitly guarded by "no `Authorization` header was presented at all" (a present header makes `require_auth` return or raise several lines earlier, `auth.py:78-82`, before it ever reaches the cookie/strict-mode branch) — a naive copy of `if is_auth_enabled() and _require_header_auth_with_cookie(): raise 401` into `require_admin` loses that implicit guard and would 401 a legitimate valid-header-plus-valid-cookie request on every one of the 11 routes that call `require_auth` then `require_admin` (a functional regression, caught in adversarial review). The correct check: `if is_auth_enabled() and _require_header_auth_with_cookie(): auth_header = (request.headers.get("authorization") or "").strip(); if not (auth_header and (_verify_bearer(auth_header) or _verify_basic(auth_header))): raise 401`. Also add `await require_auth(request)` before `require_admin(request)` in both voice-profile handlers (`web/app.py:858`, `:878`), matching every other admin route's shape, per the Problem statement's own framing ("every other mutating route calls `require_auth` first")
- AC2: Given the app's route table, when every route that depends on `require_admin` is exercised under strict mode with a cookie only, then every one returns 401 — **and**, given a valid `Authorization` header plus a valid admin cookie under the same strict mode, every route still returns 200 (the positive case that catches the regression described in AC1's mechanism note). Enumerate the route table by grepping the source for `require_admin(` call sites (there is no `Depends(require_admin)` declarative list to introspect — every current call site invokes it imperatively inside the handler body) rather than trying to derive it from `app.routes`; as of this hardening pass the call sites are `web/routers/library.py:542,753,802,825`, `web/app.py:476` (image-view permission check — read-only, not otherwise touched by this item; note in the PR body that this route's behavior under strict mode changes too, since it's a `require_admin`-only call site like voice-profile was), `:563`, `:600`, `:650`, `:683`, `:716`, `:859`, `:878`. Because AC1's fix lives inside `require_admin` itself, this AC is satisfied for all of them without visiting each call site individually. Test-shaping note: routes taking a Pydantic body (e.g. `/move`) need a valid JSON body to reach the `require_admin(request)` line at all — reuse the request-shaping already worked out in `tests/web/test_library_api.py::test_endpoints_require_admin_403` per route rather than sending an empty body to all of them
- AC3: Given a cookie session and `Authorization: Bearer nope` with no `X-Requested-With`, when `POST /api/auth/logout` is called, then the response is 403 and the session is not revoked. Mechanism: `CSRFMiddleware.dispatch` (`middleware_csrf.py:82-84`) bypasses CSRF whenever *any* `Authorization` header is present, valid or not; `api_auth_logout` (`web/app.py:409-416`) itself has no auth dependency at all, so today an invalid Bearer plus a valid cookie sails through both layers. Fix only the middleware: bypass CSRF when `_verify_bearer(auth_header) or _verify_basic(auth_header)` (imported from `web.auth`) succeeds, not merely on the header's presence. With that fix alone, an invalid Bearer no longer bypasses CSRF, the request falls through to the "browser clients: require `X-Requested-With`" branch, and is rejected there — no change to `api_auth_logout` itself is required or in scope
- AC4: Given a valid Bearer token, when a mutating route is called without `X-Requested-With`, then CSRF is bypassed as today — same code path, with `_verify_bearer`/`_verify_basic` now returning `True`
- AC5: Given an anonymous request, when `/docs`, `/redoc` or `/openapi.json` is fetched, then the response is 404. Mechanism: `FastAPI(docs_url=None, redoc_url=None, openapi_url=None, ...)` in `web/app.py:193` — FastAPI registers no routes at all for those paths, so they fall through to the app's default 404. No internal consumer of `/openapi.json` was found in this repo during hardening (searched for "openapi" and "hetzner" across `docs_v2/` and the codebase); the "optional admin-gated alternative" mentioned in Scope is genuinely optional — no AC requires it, and it is not part of this item's test-first targets. Skip it unless a concrete consumer surfaces during implementation, and say so explicitly in the PR body per the Risks item below
- AC6: Given an object in the root folder, when `POST .../move` with `target_folder=root` is called, then the response is 400 and the fake storage received no copy and no delete
- AC7: Given an object in the keep folder, when it is moved to root, then the source key is the keep-folder key. Mechanism: today `_move_in_storage` (`library.py:484-513`) hardcodes `source_folder = paths.image_folder` — it has no way to know an object's real current folder. Add `source_folder: str = "root"` to `LibraryMoveRequest` (new, optional, default preserves today's behavior exactly), validated against the same `VALID_TARGET_FOLDERS` set (`{"keep", "remove", "archive", "root"}`) used for `target_folder`, with a 400 on an invalid value. Resolve `source_folder` to a prefix the same way `dest_folder` is already resolved (mirror the existing `target_folder` if/elif chain). Compute `src_key`/`dst_key` from the resolved source/target prefixes and reject `src_key == dst_key` with 400 (this is AC6, and it subsumes the old "always root" bug: root→root is just the default-source, target=root case). Existence checking cannot reuse `ensure_known_image` for a non-root `source_folder`, because that helper only ever checks the root listing (`WebImageService._get_cached_images`) — for `source_folder != "root"` add a new `WebImageService.ensure_known_object(folder: str, filename: str) -> None` and use it instead of `ensure_known_image` for those cases; keep `ensure_known_image` (unchanged) for `source_folder == "root"` so the existing listing-cache-invalidation behavior (`tests/web/test_library_move_sanitizing.py::test_an_object_uploaded_moments_ago_can_be_moved`) is untouched. **`ensure_known_object` must enforce the same suffix gate `ensure_known_image` does, not existence alone** (`if not filename or not filename.lower().endswith(self._IMAGE_SUFFIXES): raise FileNotFoundError` — mirror `ensure_known_image`'s own first line — then `head_object`): sidecar `.txt` files live alongside images in every folder this move now reaches, so an existence-only check would let `POST /objects/sidecar.txt/move` with `source_folder=keep` relocate a raw sidecar key directly — reopening, inside this same item, the exact "no suffix/listing check lets you operate on a sidecar key" bug AC8/AC10 close for upload/delete (caught in adversarial review). Add a negative test alongside the positive one: moving a `.txt`-suffixed name with a non-root `source_folder` returns 404 and the fake storage receives no copy/delete — this needs no change to the reused `_FakeS3.head_object` fake (see AC7's mock-boundary note in the handoff), since the suffix check rejects before `head_object` is ever called
- AC8: Given a multipart upload named `foo.txt` with valid JPEG bytes, when it is submitted, then the response is 415 and nothing is written. Mechanism: `_verify_image_bytes` only checks the file's magic bytes, never the destination key's suffix — a `.txt` name today collides with the sidecar-file naming convention. After `_sanitize_filename`, before `_verify_image_bytes` (fail fast, avoid the Pillow decode for a doomed request), reject when the sanitized name does not end in `.jpg`/`.jpeg`/`.png` with `HTTPException(415, ...)`. The suffix tuple is already duplicated three times (`library.py`'s two listing helpers each define a local `_image_suffixes`, and `WebImageService._IMAGE_SUFFIXES`) — reuse `WebImageService._IMAGE_SUFFIXES` directly (`library.py` already imports the `WebImageService` class) rather than inventing a new shared module; do not have `service.py` import from `library.py` to close the loop the other way
- AC9: Given an image `a.jpg` already exists, when `a.jpg` is uploaded without `overwrite=true`, then the response is 409; with `overwrite=true` the upload succeeds. Mechanism: **hardening deviation from this item's own Implementation Notes** — implement `overwrite` as a query parameter (`overwrite: bool = False` on the route signature) rather than a multipart form field. FastAPI parses query params independently of the body, so this needs no change to the security-hardened streaming multipart parser in `_read_single_file_part` (#136) — extending that parser's state machine to also capture a second form field would add surface area to exactly the code this item is trying to make safer. A client sends `POST /api/library/upload?overwrite=true` with the same multipart body as today; check existence via `storage.head_object(key) is not None` before calling `put_object`, returning 409 when it exists and `overwrite` is not set
- AC10: Given `DELETE /api/library/objects/foo.txt` or a name not in the listing, when it is called, then the response is 404 and nothing is deleted. Mechanism: `_delete_from_storage` currently checks existence via an ad-hoc `storage.head_object(key) is None` with no suffix restriction at all, so it can delete any object key under the folder, including a sidecar `.txt` directly. Add `await service.ensure_known_image(filename)` at the top of `_delete_from_storage` (reusing the same suffix + root-listing check `move_object` already uses) — it raises `FileNotFoundError`, which the router already maps to 404 — and keep the existing `head_object` check afterward as a second guard against a listing-cache race (the file existed in the cached listing but was already deleted by a concurrent request)

- AC11: Given an object named `a.jpg` exists in BOTH the keep folder and the root folder, when `POST /objects/a.jpg/move` is called with `source_folder=keep` and `target_folder=root`, then the response is 409 and the fake storage received no copy and no delete — neither for the image nor for its sidecar. Mechanism: `_move_in_storage` (`library.py:520-550`) calls `storage.move_object(src_key, dst_key)` with no destination check, and `ManagedStorage.move_object` copies then deletes unconditionally, so an existing `dst_key` is overwritten and the source removed — the destination object and its sidecar are destroyed. Until this item, `_move_in_storage` hardcoded the source to the root folder, so every reachable move was `root → X` and a collision required the admin to already hold two copies; AC7's new `source_folder` makes `X → root` reachable and with it the most user-visible collision (clobbering an object in the listing the admin is looking at). This AC closes a hole **this item itself opened** — it is the move-side counterpart of AC9's upload 409, and the asymmetry between the two is what surfaced it in adversarial review. Check with `await storage.head_object(dst_key) is not None` before the `move_object` call, mirroring AC9's placement. **No `overwrite` escape hatch is added**, deliberately: unlike upload, replacing an object via move is not an established workflow (no UI consumer of `/move` exists — `templates/` was grepped), and an admin who genuinely wants to replace can delete the destination first. Adding an unused flag would be speculative surface on exactly the code path this item is hardening. The same accepted limitation as AC9 applies — `ManagedStorage.head_object` maps any `ClientError` to `None`, so this guard fails open on a transient non-404 fault; that is tracked as a follow-up for both call sites rather than solved here (see Risks). **Residual, accepted:** the guard covers the image key, and because it refuses before any copy or delete no sidecar is touched *in the collision case it tests*. The best-effort sidecar move at the end of `_move_in_storage` remains unguarded on its own, so an **orphaned** destination sidecar (a `.txt` with no matching image — producible via the suppressed sidecar delete in `_delete_from_storage`, or an `overwrite=true` upload, which writes the image only) can still be overwritten. The loss is a caption for an image no longer in that folder; guarding it is out of scope here

## Implementation Notes

- Two sub-issues, two PRs: #187 (auth, CSRF, OpenAPI) and #188 (move, upload, delete).
- #187 touches `web.auth` internals; AGENTS.md gates that, so the PR body states the change and the owner's merge is the approval. `security-auditor` gate mandatory.
- The `overwrite` contract addition to the upload endpoint is a **query parameter**, not a form field — see the AC9 mechanism note; default reject (existing name, no `overwrite=true` → 409).
- `require_admin`'s new strict-mode check must run *after* its existing `is_admin_request` check, not before — a request with no cookie at all must still get 403 ("Admin privileges required"), not 401 ("Header authentication required..."), even under strict mode.
- `require_admin`'s new strict-mode check must re-verify the `Authorization` header itself (`_verify_bearer`/`_verify_basic`), not just check that strict mode is configured — see the AC1 mechanism note for why the naive version regresses every route that calls `require_auth` then `require_admin` (caught in adversarial review).
- `ensure_known_object` (AC7) must apply the same `_IMAGE_SUFFIXES` gate `ensure_known_image` does, not existence alone — see the AC7 mechanism note (caught in adversarial review).
- `.claude/rules/web-security.md:12` and `docs_v2/03_Architecture/ARCHITECTURE.md:109-112` both describe the current `require_auth`/`require_admin` split and need a line added noting strict mode is now enforced inside `require_admin` itself, including for the read-only `app.py:476` view-permission call site.

## Risks

- Moving the strict check into `require_admin` must not double-count a failed attempt in the login-attempt budget. No such budget/counter exists anywhere in `publisher_v2/src/publisher_v2/web/` today (checked `web/rate_limit.py` and grepped for "login attempt"/"attempt budget") — this risk is forward-looking (relevant if one is added later, e.g. for Auth0 lockout), not something this item's implementation needs to work around today.
- Hiding OpenAPI may break an internal tool that reads it; check the Hetzner clone script before removing. No script referencing `openapi.json` was found in this repo (the "Hetzner" hits are all the unrelated `PUB-011`/epic-011 Heroku→Hetzner *app cloning* docs, which never mention OpenAPI) — flagged as unconfirmed rather than resolved, since a consumer could still exist outside this repo (e.g. in `platform-orchestrator`); note this explicitly in the PR body rather than silently assuming it's clear.
- `ManagedStorage.head_object` maps **every** `ClientError` to `None`, not just 404 (`managed_storage.py:607-621`), so both write-gating guards in this item — AC9's upload 409 and AC11's move 409 — fail **open** on a transient 403 or throttle: the object reads as absent and the write proceeds, overwriting it. Found by `security-auditor` at AC9 and confirmed to be inherited by AC11's second call site. Mitigated but not solved: the non-404 branch logs a `head_object_failed` warning (#142), and the other `head_object` callers (`ensure_known_object`, `_delete_from_storage`) fail *closed*. Needs its own roadmap item — an `object_exists(key)` that re-raises on non-404, or a 503 on the ambiguous case rather than a write. Accepted here because it requires an infrastructure fault to trigger and both guards are strictly better than the unconditional overwrite they replace.
- The existence-check-then-write in AC9 (`head_object` then `put_object`, no lock) is a plain TOCTOU race for two concurrent `overwrite=false` uploads of the same new name — consistent with the codebase's existing risk posture elsewhere in this file (e.g. `_move_in_storage`'s own check-then-act), so accepted, not a blocker.
